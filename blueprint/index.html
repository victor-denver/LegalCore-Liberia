System architecture

LegalCore West Africa is a single-page React application backed by Postgres. There is no application server of our own: the browser talks straight to the database, and Postgres row-level security — not middleware — is what enforces who may read and write what. Reading the law needs no account at all.

The one architectural idea

Most products put an API server between the client and the database so that the server can decide who is allowed to do what. This system deletes that layer and pushes the same decision into Postgres itself, as row-level security policies attached to each table.

That is why the browser can safely hold a publishable API key: the key identifies the project, it does not grant permission. Every query it makes still runs as the signed-in user — or as an anonymous visitor — and the database rejects anything the policies do not allow. One less service to run, one less place for an authorisation bug to hide.

Frontend

A conventional React SPA, organised so that state has exactly one owner. Four providers wrap the router; everything below them reads from hooks rather than passing props down.

Provider tree

  1. AuthProviderSession, profile row and isAdmin. Subscribes to Supabase auth events and keeps profiles in sync.
  2. JurisdictionProviderWhich of the 12 ECOWAS countries the visitor is browsing. Drives search scope, AI context and copy.
  3. StoreProviderSaved documents, brief items and watchlist. Local-first, merged with the cloud on sign-in.
  4. LayoutChrome: nav, command palette, announcement bar, AI dock, feedback widget, onboarding.
  5. Routes22 pages. /admin is the only one behind a guard.

Notable client capabilities

Typo-tolerant search

Ranking runs entirely in the browser against the bundled corpus, so results appear as you type and keep working offline. Misspellings still match.

Local-first library

Saving a document works signed out and persists locally. Sign in later and the local set is union-merged with the cloud — nothing is lost, and no feature is held hostage to an account.

Country-aware experience

Jurisdiction drives search scope, the AI assistant's context, and the copy shown. A visitor's choice is written to their profile and restored on any device.

Citable exports

Documents export to PDF with provenance, a QR code back to the source and a generated citation, so a brief filed in court can be traced to the instrument.

Dual theme

Every colour resolves from CSS custom properties on <html data-theme>. Theme is resolved before first paint, follows the OS by default, then remembers the choice.

Remote configuration

Announcement banner, sign-in providers, nudge threshold and the paywall switch all read from app_config — changeable from the admin console with no redeploy.

Why views, not client-side aggregation. Every view is declared security_invoker = true, which means row-level security still applies when it is queried. An aggregate is therefore admin-only by the same rules as the underlying table — the client never receives the raw rows it would need to compute these itself.

The two that pay for themselves

Zero-result searches

Every search that returned nothing, ranked by frequency and grouped by country. This is a content roadmap written by users: it names the exact laws to digitise next, in demand order.

Country activity

Sessions, searches, reads and AI questions per country. Decides which national library to open next using evidence rather than instinct.

Security model

There is no server to trust, so nothing is enforced in the UI. Access rules live in the database and apply identically to the app, a stray curl, or anyone poking at the API from a console.

Three rules

Deny by default

RLS is enabled on every table. With no policy matching, a row is invisible. Access is granted explicitly, never assumed.

Own your rows

A user may read and write only rows where user_id = auth.uid(). Admins get separate read policies through a security-definer is_admin() helper.

Privilege is not self-service

A trigger on profiles rejects any change to role or plan that did not come from an admin — so a user cannot promote themselves or grant themselves a paid plan by editing their own row.

Keys

Hard rule. Any variable prefixed VITE_ is compiled into JavaScript that every visitor downloads. Only the publishable key may ever go there. Credentials live in git-ignored files and are never committed.

Authentication

Path Status Detail
Email + password Live Sign up, sign in, reset. One door for everyone.
Magic link Wired Passwordless email sign-in.
Google OAuth Built, disabled PKCE flow ready; hidden until google_login_enabled is flipped in the admin console.
The sign-in page reveals nothing about roles. There is no "admin login" and no hint that privileged accounts exist. Administrators use the same form as everyone else and are routed by the role the database reports after authentication. Failed sign-ins return one generic message, so the form cannot be used to discover which email addresses are registered.

Privacy posture

First-party analytics only

No third-party trackers, no advertising pixels, no cookies for measurement. Events go to our own Postgres table and nowhere else.

Minimal collection

No IP addresses or fingerprints are stored. Events carry a random session id, a country, and what happened — enough to improve the product, not enough to follow a person.

Runtime flows

The four paths worth knowing, end to end.

Reading the law — no account, no network

  1. BrowserLoads the hashed bundle from the Vercel edge. The full corpus is already inside it.
  2. ClientRanks the corpus locally as the visitor types. No request is made.
  3. ClientRenders the instrument with provenance, citation and export controls.
  4. AnalyticsQueues a search and a doc_view event for later batching.

Signing in and merging a library

  1. UserSubmits email and password on a single form with no role hints.
  2. GoTrueVerifies and returns a JWT. Failures return one generic message.
  3. AuthProviderLoads the profiles row, exposing role, plan, country and isAdmin.
  4. StoreProviderFetches the cloud library and union-merges it with whatever was saved locally while signed out.
  5. PostgresAccepts the writes only for rows belonging to this user, per RLS.
  6. RouterSends admins to the console, everyone else to where they were headed.

Analytics — batched, cheap, interruption-proof

  1. Any pageCalls track(name, props). The event goes into an in-memory queue.
  2. QueueFlushes on a timer, or once the batch is full — one insert instead of dozens of requests.
  3. BrowserAlso flushes on visibilitychange and pagehide, so closing the tab does not lose the session.
  4. PostgresInsert-only for clients. Nobody can read the events table back except an admin.

Admin console

  1. Route guardProtectedRoute requireAdmin hides the page — convenience, not security.
  2. ConsoleQueries the eight insight views in parallel on load.
  3. PostgresBecause the views are security_invoker, a non-admin gets nothing — the guard is in the database.
  4. AdminTriages feedback, requests and corrections; reads insights; flips feature flags.
  5. app_configA flag change reaches every live visitor on their next config read. No deploy.

Product & revenue

Reading primary law is free and stays free — that is the mission, and it is also the moat. Revenue comes from professional workflow built on top of it.

The split

Free, permanently

  • Full-text search across every instrument
  • Read, copy, print and export any law
  • AI assistant, per country
  • Compare provisions across ECOWAS states
  • Saved library and brief builder
  • Report a correction · courts map

Free access is what earns the traffic, the goodwill and the institutional trust that nothing else in this market has.

Paid later — professional workflow

  • Citation and amendment alerts
  • Firm workspace with shared briefs and roles
  • AI memo drafting with pinned citations
  • Offline country packs
  • Branded exports with a table of authorities
  • Compliance checklists · developer API

None of it restricts access to the law. It sells time saved to people whose time is billable.

Demand before build

Every roadmap feature ships to the public plans page with an "I'd pay for this" button. Votes land in feature_interest and surface in the admin console ranked by demand. Features are built in the order users are willing to pay for them, not in the order they were imagined.

Switching revenue on

The groundwork is already in the schema: profiles.plan exists and is trigger-protected against self-service upgrades, and app_config.paywall_enabled is the single switch that turns gating on. Adding billing later is a payment webhook writing to plan plus flipping one flag — not a re-architecture.

Everything is free today. The paywall flag ships in the off position deliberately. The machinery exists so that the decision to charge is a business decision, available on any given Tuesday, rather than an engineering project.

Design decisions

The choices that shaped the system, and what each one cost. Recorded so that a future maintainer can tell a deliberate trade-off from an accident.

ADR-01No API server — RLS is the authorisation layer
Context
A small team needs authorisation it cannot get wrong.
Decision
The browser queries Postgres directly. Row-level security policies are the only access control.
Gains
No server to run, patch or pay for. One place to audit. Rules apply to every client equally, including ones we did not write.
Costs
Authorisation is expressed in SQL, which is less familiar than middleware. Policy mistakes are severe, so migrations need careful review.
ADR-02The law corpus is a build artefact, not database rows
Context
Connectivity across West Africa is uneven and often metered.
Decision
Primary law is compiled into the bundle as typed modules and served from the CDN.
Gains
Search is instant and offline-capable. Zero database cost for the most common action. Read-only data cannot be corrupted at runtime.
Costs
Publishing a new law requires a deploy, and the bundle grows with the corpus. Both become limiting as coverage expands beyond a few countries.
Revisit
Move the corpus into Postgres with full-text indexes once editors need to publish without engineers, or the bundle outgrows a cheap download.
ADR-03Local-first storage, merged on sign-in
Context
Forcing an account before a first-time visitor can save anything loses the visitor.
Decision
Saving works signed out and persists locally; signing in union-merges local and cloud state.
Gains
No feature is gated behind registration. Nothing is ever lost by signing in late. Sign-up is encouraged by value, not by a wall.
Costs
Two sources of truth to reconcile. Merge is additive, so a deletion made while signed out does not propagate.
ADR-04One sign-in door, no role hints
Context
A visible "admin login" advertises where the valuable accounts are.
Decision
Everyone uses one form. Role is read from the database after authentication and only ever affects routing.
Gains
No reconnaissance surface. Generic failure messages prevent using the form to enumerate registered emails.
Costs
Administrators get no dedicated entry point and must know to look for the console.
ADR-05Feature flags in the database, not the bundle
Context
Announcements, sign-in providers and the paywall need to change faster than a deploy cycle.
Decision
Behaviour reads from app_config, editable in the admin console.
Gains
Operational changes take seconds. A broken provider can be switched off without a rebuild.
Costs
A config read on load, and the need for sane defaults so the app still works if the fetch fails.
ADR-06First-party analytics, deliberately incomplete
Context
A legal platform must not leak what a person is researching.
Decision
Batched inserts into our own table. No third parties, no IP addresses, no fingerprints, no measurement cookies.
Gains
Credible privacy for a sensitive use case. Data stays inside the same database the rest of the product uses.
Costs
No funnel tooling out of the box, and coarser attribution than a commercial analytics product would give.
ADR-07Insights as security-invoker views
Context
Aggregates would otherwise require shipping raw rows to the client.
Decision
Aggregate in Postgres through views declared security_invoker = true.
Gains
RLS still applies to the aggregate, so a non-admin gets nothing. The client downloads summaries, not the event log.
Costs
Aggregation happens per request; heavy views will eventually need materialising.

Build & deploy

Pipeline

  1. git pushVercel picks up the commit.
  2. tsc -bWhole-project typecheck. A type error fails the build before anything ships.
  3. vite buildBundles and hashes assets. VITE_ env vars are baked in at this moment.
  4. VercelPublishes immutable assets to the global edge.
Consequence worth remembering. Because environment variables are compiled in at build time, changing one in the hosting dashboard does nothing until the next deploy. New env var, new build — always.

Environment

Variable Purpose
VITE_SUPABASE_URL Project endpoint
VITE_SUPABASE_PUBLISHABLE_KEY Browser-safe project key

Absent either one, the Supabase client is null and the app runs fully local: the law is still searchable and readable, accounts and sync are simply unavailable. Degradation is a designed state, not a crash.
